# Koyomi 产品重构需求文档（交付 Devin AI）

> 文档状态：可执行 MVP 需求  
> 目标平台：iPhone / iOS 17+  
> 开发语言：Swift 6、SwiftUI、SwiftData  
> 主要市场：日本  
> 默认语言：日语  
> 暂定产品名：Koyomi（こよみ）  

## 1. 给 Devin 的任务摘要

请将当前 Koyomi 从“每日占卜应用”重构为一款面向日本轮班工作者的极简排班日历。核心价值是：用户可以快速录入早班、晚班、夜班和休息日，在月历中一眼看清排班，并自动计算预计工资；同时能把不含工资信息的排班月历导出为图片，方便与伴侣、家人或朋友分享。

本次只实现下文定义的 MVP。不要自行扩大范围，不要加入账号系统、后端服务、社交动态、聊天、AI 排班、复杂考勤或 Android 版本。

完成后必须保证项目可编译、自动化测试通过，并在 iPhone SE 尺寸和主流大屏 iPhone 模拟器上完成基本 UI 验证。

## 3. 产品定位

### 3.1 一句话定位

日本轮班工作者可以在几秒内录入排班、查看预计工资，并把漂亮的月度排班图分享给重要的人。

### 3.2 核心用户

第一核心用户：

- 18～45 岁；
- 在日本从事护士、介护、便利店、餐饮、酒店、零售、物流或工厂工作；
- 每月存在早班、晚班、夜班、休息等不固定排班；
- 目前使用纸张、聊天软件、系统日历或复杂排班 App；
- 希望录入足够快、界面容易理解、不强制注册。

第二核心用户：

- 轮班工作者的伴侣或家人；
- 只需要通过一张图片了解对方什么时候工作、什么时候休息；
- 不需要安装本 App。

### 3.3 MVP 成功标准

技术与产品验收阶段使用以下指标：

- 新用户在首次打开后 60 秒内能完成一个班次模板和一天排班的录入；
- 已创建模板后，用户最多 3 次点击即可给某一天设置排班；
- 能在月历中区分工作、休息和未设置日期；
- 工资汇总与测试用例中的人工计算完全一致；
- 导出的排班图片不包含工资、备注或其他私密信息；
- App 无需注册、无需联网也能完成全部 MVP 核心功能；
- 冷启动、翻月和批量录入时无明显卡顿。

## 6. 详细功能需求

### 6.1 首次引导

引导最多 3 页，禁止长篇说明。

流程：

1. 价值说明：`シフトを、もっとかんたんに。`；
2. 创建第一个班次模板；
3. 可选设置基础时薪，随后进入日历。

默认提供以下模板，用户可以修改或删除：

| 名称 | 日语 | 默认时间 | 默认颜色 |
| --- | --- | --- | --- |
| 早班 | 早番 | 07:00–16:00 | 蓝色 |
| 日班 | 日勤 | 09:00–18:00 | 绿色 |
| 晚班 | 遅番 | 13:00–22:00 | 橙色 |
| 夜班 | 夜勤 | 22:00–次日 07:00 | 紫色 |
| 休息 | 休み | 无时间 | 灰色 |

要求：

- 不在启动时请求通知权限；
- 不请求位置权限；
- 用户可以跳过工资设置；
- 完成引导后保存状态，后续不重复展示；
- UI 测试模式下可以稳定跳过或完成引导。

### 6.2 班次模板

每个班次模板包含：

- `id: UUID`；
- 名称，必填，1～12 个字符；
- 类型：工作或休息；
- 开始时间；
- 结束时间；
- 是否跨日；
- 休息分钟数，默认 60，范围 0～480；
- 颜色，只能从预定义、具备足够对比度的色板中选择；
- 排序序号；
- 是否归档。

行为要求：

- 最多 12 个未归档模板；
- 支持创建、编辑、排序和归档；
- 已被历史排班使用的模板不得硬删除，改为归档；
- 日历中的历史排班必须保存模板快照，之后修改模板不能改变历史工时；
- 休息模板不显示开始/结束时间，也不计工资。

### 6.3 月历

月历要求：

- 周日开始，符合日本常见日历习惯；
- 显示星期日到星期六；
- 星期日使用可访问的红色强调，星期六使用蓝色强调，但不能只依赖颜色传达状态；
- 显示日本法定节假日名称或标记；
- 支持左右滑动翻月，也保留明确的上一月/下一月按钮；
- 提供“回到今天”按钮；
- 每个日期最多显示一个主班次标签；
- 夜班跨日时只归属于开始日期，不在次日重复创建班次；
- 已设置班次、休息、未设置必须同时通过文字或符号区分；
- 点击日期打开单日编辑 Sheet；
- 长按日期可以进入批量录入模式；
- 月份切换不应修改数据。

日本节假日数据必须通过本地、可测试的确定性算法或版本化静态数据实现，不得让月历依赖在线 API。至少覆盖当前年份前后各 5 年，并为春分日、秋分日、补休日和国民休日提供测试。

### 6.4 单日排班录入

点击日期后显示底部 Sheet：

- 日期和星期；
- 班次模板快捷按钮；
- 可选备注，最多 100 字，只保存在本机；
- 保存；
- 删除当天排班。

要求：

- 选择模板后默认一键保存或提供清晰的保存动作；
- 每个日期 MVP 只允许一个主班次；
- 重复设置同一天时更新原记录，禁止生成重复记录；
- 删除必须可撤销，至少提供短暂 Undo 提示；
- 休息日与“未设置”是不同状态。

### 6.5 批量录入

用户可选择连续日期范围，然后选择一个班次模板批量应用。

要求：

- 显示开始日、结束日和受影响天数；
- 如果范围内已有排班，保存前提示将覆盖多少天；
- 用户确认后再覆盖；
- 批量操作必须支持一次 Undo；
- 单次最多处理 62 天，避免误操作；
- 计算和持久化应在主线程安全范围内完成，不造成明显 UI 卡顿。

### 6.6 工资规则与月度汇总

基础工资设置：

- 基础时薪，单位日元，允许为空；
- 夜间加成比例，默认 25%；
- 夜间时段，默认 22:00～05:00；
- 加班加成比例，默认 25%；
- 单日标准工时，默认 8 小时；
- 交通补贴：MVP 仅支持“每个工作日固定金额”，默认 0；
- 金额只允许非负整数；
- 比例范围 0%～200%。

汇总页显示：

- 当前选择月份；
- 工作天数；
- 休息天数；
- 未设置天数；
- 总计费工时；
- 夜间工时；
- 加班工时；
- 基础工资估算；
- 夜间加成；
- 加班加成；
- 交通补贴；
- 预计工资总额。

计算规则：

1. `班次时长 = 结束时间 - 开始时间`，跨日时加 24 小时；
2. `计费工时 = max(0, 班次时长 - 休息时间)`；
3. 夜间工时按班次与夜间时段的实际交集计算；
4. 加班工时按单日计费工时超过标准工时的部分计算；
5. 基础工资覆盖全部计费工时；
6. 夜间加成和加班加成分别追加；同一时段同时满足时，两种加成可以叠加；
7. 交通补贴按工作日次数追加；
8. 计算过程使用分钟或整数秒，禁止用容易累计误差的浮点小时作为事实来源；
9. 日元最终显示四舍五入到整数；
10. 如果未设置时薪，仍显示工时统计，工资区域显示 `時給を設定すると表示されます`。

必须在汇总页明确展示：

`表示金額は概算です。実際の給与・税金・社会保険料とは異なる場合があります。`

不要声称结果是正式工资、到手工资或法律/税务建议。

### 6.7 分享排班图片

用户可以从月历页导出 1080 × 1350 的竖版 PNG。

图片包含：

- 年月；
- 月历网格；
- 每天的班次简称或休息标记；
- 班次颜色图例；
- `Koyomi` 品牌小字。

图片绝对不能包含：

- 时薪；
- 预计工资；
- 加成规则；
- 每日备注；
- 用户姓名；
- 设备标识符；
- 广告。

分享前必须显示预览。使用系统 Share Sheet，不接入自建上传服务器。无排班的月份也允许分享，但应提示图片内容为空。

### 6.8 本地提醒

提供两个独立开关：

1. 每月录入提醒，例如每月 25 日 20:00；
2. 次日班次提醒，例如前一天 20:00。

要求：

- 只有用户主动打开任一开关时才请求通知权限；
- 权限被拒绝后显示前往系统设置的说明，不循环请求；
- 修改或删除排班后同步更新相关通知；
- 通知内容不显示工资和备注；
- 夜班提醒必须显示正确的开始日期和时间。

### 6.9 数据管理

MVP 所有业务数据默认只存储在本机。

需要支持：

- 导出 JSON 备份；
- 从 JSON 导入；
- 导入前验证 schema version；
- 导入前显示“合并”或“替换”选项；
- 替换属于破坏性操作，必须二次确认；
- 导入失败不能破坏现有数据；
- 删除全部数据需要二次确认；
- 删除后恢复为首次启动状态。

JSON 不必加密，但导出界面应提醒文件可能包含排班、备注和工资设置，请谨慎保管。

## 7. 数据模型建议

可调整命名，但语义必须保持清晰。

### 7.1 `UserSettingsRecord`

- `onboardingCompleted: Bool`
- `hourlyWageYen: Int?`
- `nightPremiumBasisPoints: Int`，25% 存为 2500；
- `overtimePremiumBasisPoints: Int`；
- `nightStartMinute: Int`；
- `nightEndMinute: Int`；
- `standardDailyMinutes: Int`；
- `transportAllowancePerWorkdayYen: Int`；
- `monthlyReminderEnabled: Bool`
- `monthlyReminderDay: Int`
- `monthlyReminderMinuteOfDay: Int`
- `nextShiftReminderEnabled: Bool`
- `nextShiftReminderMinuteOfDay: Int`
- `backupSchemaVersion: Int`

### 7.2 `ShiftTemplateRecord`

- `id: UUID`
- `name: String`
- `kindRawValue: String`
- `startMinute: Int?`
- `endMinute: Int?`
- `crossesMidnight: Bool`
- `breakMinutes: Int`
- `colorRawValue: String`
- `sortOrder: Int`
- `isArchived: Bool`
- `createdAt: Date`
- `updatedAt: Date`

### 7.3 `ShiftEntryRecord`

- `id: UUID`
- `dayKey: String`，格式 `yyyy-MM-dd`，唯一；
- `templateID: UUID?`；
- 模板快照：名称、类型、开始分钟、结束分钟、跨日、休息分钟、颜色；
- `note: String`
- `createdAt: Date`
- `updatedAt: Date`

### 7.4 约束

- 所有日历计算使用 `Asia/Tokyo` 和 Gregorian Calendar；
- `dayKey` 必须通过单一公共函数生成；
- 不以 UTC 日期字符串直接代表用户日历日期；
- SwiftData 写入必须通过 Store/Repository 层，不允许多个 View 随意直接修改 `ModelContext`；
- 给备份格式设置显式 schema version；
- 旧版 SwiftData 数据迁移必须安全：如无法合理映射，占卜数据可删除，但不得导致启动崩溃。开发构建中应有可重复验证的迁移策略。

## 9. 视觉与交互要求

产品气质：温和、清晰、日系、适合长期每天查看。不要继续使用强烈的占星或神秘学视觉语言。

设计要求：

- 支持浅色和深色模式；
- 保留柔和色彩，但提高文字和班次标签对比度；
- 主要点击区域至少 44 × 44 pt；
- 支持 Dynamic Type，至少验证 Accessibility Large；
- 支持 VoiceOver；
- 状态不能只用颜色表示，必须同时有文字、简称、图标或形状；
- 工资属于敏感信息：汇总页在 App 切换器快照时应使用系统提供的合理隐私遮挡方案，或至少提供用户可启用的隐私遮挡开关；
- 错误信息使用可操作的日语，不显示底层技术错误；
- 空状态要告诉用户下一步，例如 `日付をタップしてシフトを登録しましょう`。

日语文案必须自然，避免机器直译。代码标识符使用英文。

## 10. 广告与未来收费边界

MVP 保留现有 AdMob 横幅，但遵守：

- 引导页、数据删除确认、分享图片及分享预览不显示广告；
- 广告不得覆盖 Tab Bar、保存按钮或日期编辑 Sheet；
- 未取得适用的同意前不得请求个性化广告；
- UI 测试和截图测试完全禁用广告；
- App 核心功能在广告加载失败时必须正常工作。

未来 Pro 版候选功能仅做架构预留：无广告、无限模板、高级主题、iCloud 同步、情侣共享。不要在本次实现不可购买的 Pro 页面。

- 不接入通讯录；
- 不上传工资、排班或备注；
- 通知仅在本机调度；

- 更新 `Info.plist`，删除不再使用的位置权限文案；
- 检查 Privacy Manifest 与 App Store Privacy Label 建议是否和实际代码一致。

## 12. 自动化测试要求

### 12.1 `KoyomiCore` 单元测试（必须）

至少覆盖：

1. 09:00～18:00、休息 60 分钟 = 480 计费分钟；
2. 22:00～次日 07:00、休息 60 分钟的跨日时长；
3. 夜间时段 22:00～05:00 的交集；
4. 班次只覆盖部分夜间时段；
