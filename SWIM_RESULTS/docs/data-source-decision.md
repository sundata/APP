# データ取得方式の決定：Mode B（公式サイト遷移）を MVP とする

- 決定日：2026-09-02
- 根拠となる調査：`docs/source-investigation.md`
- ステータス：**Mode B で実装。Mode A は未承認のため実装しない**（プロダクトオーナー承認・連盟の許諾が得られるまで）

## 1. 結論

| 項目 | 判断 |
| --- | --- |
| 採用モード | **Mode B：公式サイト遷移** |
| アプリ内での結果データ取得 | **行わない**（`/api/v1/*` の呼び出し、HTML 解析、WebView への DOM 注入・自動入力はいずれも実装しない） |
| アプリが保持するデータ | 端末内の検索履歴（検索条件と公式 URL のみ）とお気に入り（名称 + 公式 URL のみ） |
| 公式サイトへのリクエスト | ユーザーが「公式サイトで開く」を押したときに `SFSafariViewController` が 1 ページを開くのみ。アプリ自身は結果サイトに一切リクエストを送らない |

## 2. 法務・規約上の根拠

1. **利用許諾が確認できない。** 結果サイトには利用規約・API 利用条件・問い合わせ窓口の記載がなく、連盟本体サイトは調査時点で障害中のため規約を確認できなかった。指示書 §2-6 により、許可が確認できない場合はスクレイピングを実装せず Mode B とする。
2. **API は非公開・非文書化。** `/api/v1/*` は同一オリジンの SPA 専用として動いており、`x-ratelimit-*` ヘッダーによるレート制限と、非ブラウザ UA に対する 403 応答がある。運営側がプログラムからの利用を歓迎していないと解釈するのが妥当で、「API が見つかっても利用可と推定しない」（§2-4）に該当する。
3. **著作権・データベース権。** `©Japan Aquatics` の表記があり、結果本文を転載・複製する権利はない。Mode B ではアプリが結果本文を保持しないため、この問題を回避できる。
4. **個人情報。** 選手名・所属・学年は公開結果であっても個人に関する情報である。アプリで独自 DB を作らない Mode B なら、アプリ事業者が第三者の個人情報を取得・保管しない。検索履歴は端末内のみ。

## 3. 技術上の根拠

1. **URL パラメータでの検索条件引き渡しが非対応**（`/player-search?name=…` は無視される）。したがって「アプリで入力した名前を公式フォームへ渡す」ことは公式に保証された手段では実現できない。指示書 §5 Mode B の通り、`SFSafariViewController` で検索ページを開き、ユーザーが公式フォームに入力する。アプリ側では入力した名前をクリップボードへコピーできるようにし、公式フォームへの貼り付けを 1 タップにする（DOM 注入ではない）。
2. **安定した公開 URL がある。** `/player-search`、`/tournament/list`、`/tournament/{id}`、`/athletes/{id}`、レース結果 URL は公式側が共有ボタン（LINE/Twitter/Facebook/リンクコピー）を用意しており、URL を保存・再訪することは公式の想定内と判断できる。よって「お気に入り」には公式 URL を保存する。
3. **仕様変更耐性。** Mode B はサイト構造に依存しないため、HTML/API が変わっても壊れない。Safari 内で公式の最新画面がそのまま表示される。

## 4. アプリが提供する価値（Mode B）

- 「選手から探す」「大会から探す」の 2 動線で、該当する公式検索ページをワンタップで開く
- 入力した選手名・大会名の空白正規化 + クリップボードコピー（公式フォームに貼り付けやすく）
- 直近の検索（最大 10 件、端末内のみ）と、公式 URL のお気に入り（選手ページ・大会ページ・レース結果ページ）
- 公式サイトの使い方ガイド（決勝 / タイム決勝 / 予選の見分け方、同姓同名の識別方法）
- 情報源・非公式である旨・免責・プライバシーポリシーの明示

## 5. Mode A へ移行する条件

以下がすべて満たされた場合のみ、Phase 2 として Mode A の実装を検討する。

1. 日本水泳連盟（Japan Aquatics）から、結果データの API 利用・アプリ内表示について**文書による許可**が得られる
2. 許可の範囲（表示可能項目、キャッシュ期間、リクエスト頻度、クレジット表記、削除・訂正時の対応）が明文化される
3. 自社バックエンド（`SwimResultsProvider`）でレート制御・キャッシュ・監視・契約テストを実装する体制がある
4. プロダクトオーナーの承認

Mode A 実装時も `SwimFinderCore` の `SwimResultsProviding` プロトコルと `FinalResultPolicy`（決勝 > タイム決勝 > 公式が最終と明示 > それ以外は「区分を公式ページで確認」）をそのまま使う。モデルは実データ確認後に確定し、fixture は匿名化して保存する。

## 6. リスクと対策

| リスク | 対策 |
| --- | --- |
| 公式サイトの URL 構造変更で、保存済みお気に入りが 404 になる | お気に入りは URL のみ保存し、公式トップへの導線を常に併記。`OfficialSite` の URL 定義を 1 か所に集約し、変更時はアプリ更新で対応 |
| 公式サイト障害（調査時に連盟本体サイトが障害中） | Safari 内で公式のエラーがそのまま見える。アプリは「公式サイトに接続できない場合は時間をおいて再試行」を案内 |
| ユーザーが「公式アプリ」と誤認する | ホーム・設定・App Store 説明文に「非公式」「情報源：日本水泳連盟 結果サイト」を明記。連盟名・ロゴ・配色をブランドとして使わない |
| 検索語（氏名）のプライバシー | 端末内 SwiftData のみ。分析 SDK なし。設定から一括削除可 |
