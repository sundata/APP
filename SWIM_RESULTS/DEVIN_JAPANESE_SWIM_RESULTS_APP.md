# Devin AI 開発指示書：日本の競泳結果検索アプリ「Swim Finder（仮）」

> **この文書をそのまま Devin AI に渡してください。** まず調査と権利確認を完了し、調査結果を文書化してから実装してください。未確認の API、HTML 構造、利用許諾を推測して実装しないこと。

## 1. プロダクト概要

日本語で選手名または大会名を入力するだけで、競泳の**確定した最終結果**へ最短で到達できる iPhone アプリを作る。

- 仮称：**Swim Finder（スイムファインダー）**
- 対象：選手、保護者、コーチ、競泳ファン
- 情報源候補：日本水泳連盟の公式結果サイト
  - <https://result.swim.or.jp/>
  - <https://result.swim.or.jp/player-search>
- MVP の価値：複雑な条件入力を減らし、「選手から探す」「大会から探す」の 2 動線で公式の確定結果を見つける
- 表示言語：日本語
- 対象 OS：iOS 17 以降

本アプリは日本水泳連盟の公式アプリであるかのように見せてはならない。許諾がない限り、連盟名、ロゴ、サイトのデザインをブランドとして利用しない。

## 2. 最重要ルール（調査前に固定しないこと）

指定サイトは外部サービスであり、公開 API の有無、利用規約、robots.txt、レート制限、転載可否、個人情報の取扱い、HTML/JavaScript の実装は変更され得る。したがって Devin は次の順で進めること。

1. サイトをブラウザで実際に操作し、現行の検索項目と遷移を確認する。
2. 利用規約、プライバシーポリシー、robots.txt、著作権表記、問い合わせ窓口を確認する。
3. ブラウザの Network パネルで、検索が公開 API、HTML フォーム、JavaScript のどれで行われるか確認する。
4. API が見つかっても、アプリからの利用・再配布が許可されているとは推定しない。正式な許可または公開仕様を確認する。
5. 調査結果を `docs/source-investigation.md` に、確認日・URL・画面・入力項目・リクエスト方式・規約上の判断・未解決事項とともに記録する。認証情報や Cookie は記録しない。
6. 許可が確認できない場合はスクレイピングを実装せず、後述の **公式サイト遷移モード**を MVP とする。

### 禁止事項

- CAPTCHA、WAF、アクセス制限、認証、レート制限の回避
- 非公開 API の固定 URL を憶測でハードコード
- HTML を高頻度で巡回・全件収集し、独自データベースとして複製
- 選手の生年月日、住所、連絡先など、結果検索に不要な個人情報の収集
- 公式結果をアプリ側で改変、推測、補完して「確定結果」と表示
- サイトの HTML 構造が変わった際に、空データを「該当なし」と誤表示

## 3. Devin が現行サイトで確認する検索機能

以下は**要求候補**であり、現在のサイト仕様として断定しない。実画面に存在する項目だけを採用し、名称・必須条件・選択肢・組み合わせ制約を調査文書に転記する。

### 3.1 選手から検索

`/player-search` を起点に、少なくとも次を確認する。

- 選手名の入力形式（漢字、ひらがな、カタカナ、姓と名、部分一致/完全一致）
- 性別、所属、都道府県、年度などの絞り込みの有無
- 同姓同名を識別するため公式画面に表示される情報
- 検索結果のページング、並び順、最大件数、0 件・複数件時の挙動
- 選手詳細から確認できる大会、種目、距離、泳法、ラウンド、記録、順位
- 予選・準決勝・決勝・タイム決勝の区別、および失格・棄権等の表記
- リレーと個人種目の表示方法

期待するユーザーフロー：

1. 「選手から探す」を選択する。
2. 選手名を日本語で入力する。
3. 候補一覧から、公式サイトが提供する識別情報を見て本人を選ぶ。
4. 大会履歴を新しい順に見る。
5. 大会を選び、種目別の**公式最終結果**を見る。

### 3.2 大会名から検索

トップページおよび関連する大会検索画面を起点に、次を確認する。

- 大会名の検索方法（自由入力、候補選択、一覧から選択）
- 開催年/年度、期間、開催地、主催区分などの絞り込みの有無
- 大会名の部分一致、表記揺れ、略称への対応
- 開催中、終了、結果確定などの状態表示の有無
- 大会詳細にある日程、競技番号、種目、性別、距離、ラウンドの構造
- 最終順位、氏名、所属、記録、大会記録等の表示項目
- PDF、外部ページ、Live Results など別形式への遷移の有無

期待するユーザーフロー：

1. 「大会から探す」を選択する。
2. 大会名の一部を入力し、必要なら開催年を選ぶ。
3. 候補から大会を選ぶ。
4. 日付・性別・種目・距離・ラウンドを絞り込む。
5. **決勝またはタイム決勝を優先**して最終順位と記録を見る。
6. 「公式ページで確認」から必ず原典を開ける。

### 3.3 「最終結果」の定義

アプリが勝手に判定してはならない。公式データにラウンド/状態がある場合のみ、次の優先順位で表示する。

1. `決勝` と明示された確定結果
2. `タイム決勝` と明示された確定結果
3. 公式側で最終順位または総合結果と明示された結果

予選や速報しか存在しない場合は「最終結果」と呼ばず、公式表記をそのまま表示する。状態を確認できない場合は「結果区分を公式ページで確認してください」とする。取得日時と「公式サイトで最新情報を確認」のリンクを常に表示する。

## 4. MVP の画面

### 4.1 ホーム

- 大きな 2 ボタン：「選手から探す」「大会から探す」
- 直近の検索（端末内のみ、最大 10 件）
- 情報源と非公式アプリである旨を明記
- 設定から検索履歴を一括削除可能

### 4.2 選手検索

- 検索フィールドのラベル：「選手名」
- 例：「山田 花子」
- 入力中のリクエストは 400 ms debounce。2 文字未満で送信しない（公式仕様がより厳しい場合は従う）
- 候補には公式側が返す情報だけを表示し、推測した年齢や所属を付けない
- 0 件時：「選手が見つかりませんでした。漢字・かな・姓名の間隔を変えてお試しください。」
- 複数候補時はユーザーに選ばせ、アプリが自動確定しない

### 4.3 選手詳細・結果

- 選手名、公式側の識別情報、大会履歴
- 大会 → 種目 → ラウンドの順で表示
- 結果行：順位、記録、種目、距離、ラウンド、所属（提供される場合のみ）
- `決勝` / `タイム決勝` を目立つチップで表示
- 「公式ページで確認」ボタン

### 4.4 大会検索

- 検索フィールドのラベル：「大会名」
- 年/年度フィルター（公式検索で使用できる場合のみ）
- 候補：正式大会名、開催日、開催地（公式側が提供する範囲）
- 同名大会は開催日を必ず併記

### 4.5 大会詳細・最終結果

- 正式大会名、開催期間、会場（提供される場合のみ）
- フィルター：日付、男女、泳法、距離、ラウンド
- 初期表示は確定した決勝/タイム決勝を優先。ただし「すべて」に切替可能
- 順位表は Dynamic Type でも横スクロールに依存しすぎないカード表示
- 選手をタップすると選手詳細へ移動
- 公式 URL と取得日時を表示

### 4.6 状態画面

- 初回ロード、再読込、オフライン、タイムアウト、公式サイト障害、仕様変更の疑いを区別
- パーサー失敗や必須フィールド欠落は「該当なし」ではなく「現在、結果を取得できません」
- 最後に正常取得したデータがある場合は、日時を明示して閲覧可能にする

## 5. データ取得方式：許諾に応じた 2 モード

### Mode A：許可済み API/データ連携（推奨）

公式に利用可能な API またはデータ提供の許可が得られた場合のみ採用する。

- iOS アプリから公式サービスへ直接大量アクセスさせず、自社バックエンドに `SwimResultsProvider` を置く
- API キー、Cookie、秘密情報をアプリに埋め込まない
- キャッシュ、指数バックオフ、タイムアウト、レート制限を実装
- 原文データと正規化データを分け、公式値を追跡可能にする
- 仕様変更を検知する契約テストと監視を用意
- 削除/訂正が原典に反映された場合、キャッシュにも反映する

### Mode B：公式サイト遷移（許諾未確認時の安全な MVP）

- アプリで入力した選手名/大会名を、公式サイトが正式にサポートする URL またはフォームへ渡す
- パラメータ付き URL が公式に保証されない場合、`SFSafariViewController` で検索ページを開き、ユーザーが公式フォームに入力する
- WebView の DOM 注入、自動クリック、HTML 抽出はしない
- アプリ内には検索履歴とお気に入りの**検索条件/公式 URL**だけを保存し、公式結果本文を転載しない

Mode B でも「ワンタップで公式検索を開く」価値を提供する。許可がないのに Mode A 相当の画面を作らない。

## 6. 推奨技術構成

- Swift 6、SwiftUI、iOS 17+
- `async/await`、`URLSession`
- Safari 表示：`SFSafariViewController`
- ローカル履歴/お気に入り：SwiftData（CloudKit 同期は MVP 外）
- アーキテクチャ：Feature 単位 + MVVM、依存性注入
- バックエンドが必要な場合：TypeScript + Fastify または Next.js Route Handlers、PostgreSQL、Redis
- ログに氏名、検索語、完全な公式レスポンス、IP と検索語の組を残さない

最低限のプロトコル：

```swift
protocol SwimResultsProviding: Sendable {
    func searchPlayers(query: PlayerQuery) async throws -> [PlayerSummary]
    func playerResults(playerID: String) async throws -> [SwimResult]
    func searchMeets(query: MeetQuery) async throws -> [MeetSummary]
    func meetResults(meetID: String, filter: ResultFilter) async throws -> [SwimResult]
}
```

モデルは実調査後に確定する。例示モデルに合わせて公式レスポンスを捨てたり、存在しない値を生成したりしない。ID は公式が提供する安定 ID のみ使用し、氏名から独自生成しない。

## 7. 品質・プライバシー・アクセシビリティ

- 検索履歴はデフォルトで端末内のみ。分析 SDK へ氏名を送信しない
- お気に入り選手機能を入れる場合、本人同意が不要な公開結果であっても公開範囲を拡大しない
- プライバシーポリシー、データ削除方法、情報源、免責、問い合わせ先をアプリ内に掲載
- VoiceOver ラベル、Dynamic Type、44 pt 以上のタップ領域、十分なコントラスト
- 色だけで順位、失格、ラウンドを区別しない
- 日本語 VoiceOver の読み順をテスト
- 記録は文字列として公式表記を保持し、秒への変換は補助値に限定する
- タイムゾーンは大会情報に従い、不明なら日本時間と決めつけない

## 8. テスト要件

### Unit tests

- 選手名・大会名の空白正規化（原文は保持）
- debounce と検索キャンセル
- 決勝/タイム決勝の優先表示。ただし不明状態を決勝扱いしない
- 同姓同名、同名大会、0 件、ページング
- DNS エラー、オフライン、429、5xx、タイムアウト、壊れたレスポンス
- キャッシュ日時と期限切れ表示

### Integration / contract tests

- 許可済み API の fixture をリポジトリに匿名化して保存
- 必須フィールドや enum が変化したら CI を失敗させる
- 本番サイトに対する CI の高頻度 E2E は行わない
- 公式側のテスト環境がある場合のみ、低頻度 smoke test を行う

### UI tests

1. 選手名 → 複数候補 → 本人選択 → 大会 → 決勝結果 → 公式ページ
2. 大会名 + 年 → 大会選択 → 種目絞り込み → タイム決勝結果
3. オフライン時に古いキャッシュの日時が表示される
4. 仕様変更を模した不正レスポンスで「0 件」と誤表示しない
5. 特大 Dynamic Type と VoiceOver で主要操作が完了する

- SNS、チャット、選手へのメッセージ
- 全選手・全大会の一括収集
- 大会エントリー、決済、ライブ配信
- 公式許可前の通知、結果本文の共有画像、ウィジェット

## 10. 実装順序

### Phase 0：調査と Go/No-Go

1. 指定 2 URL を PC/モバイルで調査する。
2. 選手検索・大会検索・結果詳細の画面遷移図と項目表を作る。
3. 利用規約と技術方式を確認し、Mode A / Mode B を提案する。
4. `docs/source-investigation.md` と `docs/data-source-decision.md` を提出する。
5. **プロダクトオーナーの承認を得るまで外部データ取得コードを書かない。**

### Phase 1：デザインとローカル実装

1. 日本語 UI のワイヤーフレームを作る。
2. Provider protocol と fixture ベースの mock を作る。
3. ホーム、検索、候補、詳細、結果、エラー画面を実装する。
4. SwiftData の履歴/お気に入りと削除機能を実装する。
5. Unit/UI tests を追加する。

### Phase 2：承認済み連携

1. 承認された Mode の Provider を実装する。
2. レート制御、キャッシュ、監視、エラー分類を追加する。
3. 実データで日本語表記、同姓同名、決勝判定を QA する。
4. Privacy Nutrition Label と App Store 審査メモを作成する。

## 11. 受け入れ条件（Given / When / Then）

1. **選手検索**：Given 利用可能なデータ連携、When ユーザーが選手名を入力、Then 候補を表示し、選択後 3 タップ以内でその選手の大会別結果へ到達できる。
2. **大会検索**：Given 大会名の一部と開催年、When 検索、Then 同名大会を日付付きで区別でき、種目別の結果へ到達できる。
3. **最終結果**：Given 予選と決勝がある、When 大会詳細を開く、Then 決勝を優先し、予選を最終結果と誤表示しない。
4. **原典確認**：Given 任意の結果、When 「公式ページで確認」を押す、Then 対応する公式ページ、または最も近い公式検索ページが Safari で開く。
5. **障害**：Given 公式仕様が変わり解析不能、When 検索、Then 0 件ではなく取得エラーと再試行/公式サイトへの導線を表示する。
6. **許諾未確認**：Given API/転載許諾がない、When MVP をビルド、Then Mode B のみが有効で、HTML スクレイピングを含まない。
7. **プライバシー**：Given 検索履歴がある、When ユーザーが全削除、Then 端末内から即時削除され、分析ログに氏名が残らない。
